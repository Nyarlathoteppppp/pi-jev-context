# v0.6 Freshness-Aware Deterministic Read Dedupe

## Scope

v0.6 extends the v0.5 read dedupe matcher. The fresh-output sieve and Jev transport are unchanged.

A read can fold only when all of these conditions hold:

- The source result is visible in Pi's current active branch context.
- The path strings are identical.
- The source and incoming read use the same absolute file positions.
- The source result is an unshortened, successful, text-only read.
- Both reads belong to the same latest-user-message task epoch.
- The source result is no more than `dedupeMaxAgeTokens` estimated tokens behind the incoming read.
- The existing minimum run and savings thresholds pass.

The default `dedupeMaxAgeTokens` is `12000`.

## Task Epoch

The task epoch is the ordinal count of user messages in the active context. A source read's epoch is the count before its tool result; the incoming read uses the count of user messages currently visible before its result is appended. A new user message therefore makes all earlier reads stale without requiring a time clock or semantic interpretation.

Messages removed by fork navigation or native compaction are not available as evidence. Resume and session-tree rebuilds reconstruct the matcher from `buildContextEntries()` and do not persist freshness state separately. For read evidence only, a visible custom message, branch summary, compaction summary, or unmodeled message role is a conservative boundary: sources preceding it are not used. Plain custom storage entries (including recall originals and telemetry) are ignored and are never evidence. The v0.5 sieve context projection is unchanged.

## Token Age

For an eligible source result, age is the sum of estimated tokens in modeled message content after that tool result and before the incoming read. User content, assistant text/thinking/tool-call arguments, and tool-result text are counted. The incoming read output is not counted. Each message is estimated as `ceil(characters / 4)`; suffix sums avoid recounting the same messages for every candidate. This is not a provider tokenizer.

A source at or below the configured limit is eligible. A source above it is ignored. The default limit is intentionally finite so visible but old context does not authorize a new collapse.

## Source Selection and Partial Overlap

Candidates are considered newest first. The first candidate with an exact line-range match wins; older candidates are not combined with it. This prevents an old wide read from filling gaps around a newer partial read.

For example, if the newest eligible source covers lines `80-130`, a new read covering `50-150` can fold only `80-130`. The other lines remain verbatim. A stale full read is returned unchanged, and because it remains in context it becomes the new fresh source for an immediate later read.

## Configuration Safety

`dedupeMaxAgeTokens` resolves as extension options > environment > settings file > default. It must be a finite safe nonnegative integer. An explicitly invalid option (including `null` or `undefined`) or environment value uses `12000` instead of inheriting a potentially larger lower-priority value. An invalid file value also uses the default. The fallback is the default window, not a promise to preserve a smaller lower-priority window. Zero is valid: only age-zero evidence is eligible, so even a subsequent read's tool-call arguments can force a refresh. The top-level setting overrides the internal `seen.dedupeMaxAgeTokens` field.

## Measurement

The focused benchmark is offline and deterministic:

```sh
node bench/live/v06-freshness.ts --out /tmp/live-v06-freshness-new.json
```

The runner asserts expected behavior before writing results and refuses to overwrite an existing output path. Choose a new output path for each run. The recorded fixture run reports 14 reads, 4 fresh dedupes, 1 stale refresh, 1 prevented cross-user-turn dedupe, 1 partial-overlap dedupe, and approximately 6,166 estimated tokens saved. These are character/4 estimates, not billed provider-token savings.

## Non-goals

v0.6 does not use Jev, embeddings, semantic similarity, summaries, attention prediction, disk caches, or folded output as evidence. It does not modify the v0.5 fresh-output sieve.
